## 4. Testing rules (catch the bug before a human can see it)
The Pocket answers only what a desk cannot: timing margin of the real fit, electrical and display behaviour, the SD card and the host's own behaviour. Everything else is proven on the host first, and a change is not done until its tests have run.
1. **Test in tiers; the depth follows the risk (decided 2026-11-13: the full mutant sweep of everything after every small edit cost 15 to 25 minutes a time and found nothing the targeted run had not).**

   | Tier | When | What runs | About |
   |---|---|---|---|
   | **A, the edit loop** | while writing | the plain tests of the target you touch (`python3 sim/test_X.py`, no `--mutants`) | seconds to a minute |
   | **B, before a commit** (firmware, tools, host code) | every commit | `make test-gallery-quick` (plain tests of the gallery firmware and tools) plus the **mutants of the code you added or changed only** (hand-written, each must fail a test; run just those: `--v1-mutants N` takes the last N of the app list, or run the one test's `--mutants`) | a few minutes |
   | **C, the full sweep** | a **critical feature** or a **pre-release** (below) | every suite of the area with ALL its mutants (`make test-gallery-*`, `make test`), the ladder verdict (`make verdict`), and for RTL the whole of items 2 to 4 | 20 to 40 minutes |
   | **RTL** | any change to a block | always the full approach: a bit-exact reference test AND the whole mutation sweep of that block, CDC testbenches, probe, whole-core simulation (items 2 to 4). RTL is expensive to get wrong (a fit is 1h45) and the sweeps are short: no tiering here | per block |

   **Critical** means a failure there loses or corrupts the user's data or bricks a card, or is invisible until a person is hurt by it: anything that writes the SD card or the settings file, the installer, file and index parsers (container, index, tile index), the hardware decoder driver and its DMA handshakes, anything on the path of a pictures' bits to the screen, and any feature the owner marks critical. **Pre-release** means a tagged release, or a package the owner will keep using (not a `DEV NN` built for one quick Pocket test: that one is Tier B plus the plain tests of the whole area). A new feature always gets a test that fails when the feature is removed; the mutants are how that is proven, once, when the feature is written. Old mutants are rerun when the code they target changes, or in Tier C.

   **Mutants, the rule that stays:** a first run that passes is a smell, not a result: run the new code's mutants. A surviving mutant is either a weak test (add the test) or an equivalent mutant (prove it by enumeration, say so in the audit entry, drop it). Every block of RTL has a bit-exact reference (Python or C model, or frozen vectors). **A mutant run only counts on a passing unmutated test** (with a failing one every mutant reads "killed"): the gallery app harness and the converter-mode harness now run the plain test first and refuse to go on; check that any harness you write or copy does the same. A mutant's text is changed at its first occurrence, so keep the text unique and re-run after a refactor (a text that no longer exists stops the run). The app test's scripted key list lives in a fixed array: a scenario that outgrows it now says so and exits 2 instead of dying silently (KB-252 in the analogue-pocket-dev skill).

   **Habits that keep the cost down:** run long jobs in the background with a stated finish time and do other work meanwhile; never start a second copy of a run that is still going and never kill one halfway without restarting it cleanly; do not rerun a whole suite for an edit to a test file, rerun that test; say in the audit entry which tier ran.
2. **Clock-domain crossings are tested with unrelated clocks.** A dedicated testbench per crossing, odd phases and ratios, random traffic, clears and errors; only toggles, Gray counters and data that is stable before the pointer move may cross; never reset a toggle with the system reset.
3. **Timing is a test, and it runs before the full fit** (1h35m to 1h45m). A new or changed block gets a probe (`python3 tools/block_probe.py launch NAME unit|ent`, minutes, needs the owner's yes and a stated finish time like any VM run); integrate only a block whose probe meets setup at its real clock at the slow 85C corner with at least 0.5 ns to spare; put the Fmax in the audit entry. The m1c fit missed by 5 ns on a block that was bit-exact in simulation.
4. **Whole-core simulation before hardware or a fit** (STATE 2026-11-12: the CPU runs the firmware (issue 026 fixed, B-1072) and the run ends with a CPU self-check, `FULLCORE CPU PASSED`; `make test-fullcore-frame` (about 16 min) adds a bit-exact GOLDEN FRAME 20 ms after reset exit (change it only with `make update-golden-fullcore` after looking at the frame); a run of a few ms covers boot, the host protocol and the first target command, not a whole gallery session: say how many ms and what was reached in the audit entry) when a change touches `core_top`, `tau_soc`, `core_game.vh`, a PLL, the SDC, the bridge wiring or the SDRAM path: `python3 sim/fullcore/run.py` (the real VexRiscv, the SDRAM PHY against the timing-checked chip model, scan-out, a model of the Pocket's host; docs/FULLCORE_SIM.md). Per-block tests do not catch wiring (an unconnected input put X into the CPU). Intel's `altera_mf.v` is read from `work/quartus_sim_lib/` and is never committed.
5. **No known-failing test stays in the suite.** Fix it, or move it out with an entry in `docs/issues/` the same session (owner, date, reason). `make test` is expected green at Tier C; before every commit run Tier B for what you touched and say in the audit entry which tier ran and what did not. Makefile rules must work with spaces in the path (quote `"$(RV_BIN)/..."`).
6. **A bug found on the Pocket becomes a test first.** Reproduce it on the host (or in the whole-core simulation), watch the test fail, then fix; keep the screenshot or report beside the audit entry.
7. **Frozen specifications and vectors change only as a new version** (symbol layer, reconstruction, container); a test is never edited to make it pass: find the cause.
8. **Report honestly.** Say what was simulated, what was synthesised, what was fitted and what ran on a Pocket, and what was not run.

## Subagent delegation policy
**Rule 10 of `docs/PROJECT_RULES.md` is mandatory: mechanical work goes to a Haiku subagent** (`model: haiku`). What counts, what never does (design, RTL, firmware and converter logic, judging results, owner decisions, and every card write, install, removal, commit or push), and how to check the report are there. In short:
- Delegate: test and suite runs that report pass or fail, log and report scanning, collecting numbers into tables, mechanical edits with a stated rule, file listings and counts, summaries of long output, checksum and link checks.
- Prompt: short, with the exact files and commands, the output format and a cap on what comes back (only the returned text re-enters this context). One well-scoped subagent over several redundant ones; independent ones in parallel.
- Do not spawn one for a single quick command, or when the prompt would be as long as the work.
- A subagent's note is its report, not proof: re-run the deciding command or read the diff before it goes into a commit or an audit entry.
