# Review of docs/M2_DESIGN.md (2026-11-09): image codec and Analogue Pocket view

Reviewer's stance: an image-codec specialist and a senior Pocket developer, working from the design, the project's measured numbers (M0 and M1, B-1005 to B-1017) and the analogue-pocket-dev knowledge base. Evidence is labelled as the KB does: hardware-validated (a Pocket run of ours), docs, source, community-reported (a lead, not a fact) or derived (arithmetic from two of those). Nothing here was run on a Pocket. The design is sound in shape (measure first, reuse the proven landing path, freeze the viewport rules, keep raw levels optional). The findings below are the holes to close before M2.1 freezes the formats.

## Verdict
Proceed with M2.0 and M2.1, **after** the two blocking points are written into the design: the resident plane geometry and tearing. Add the listed measurements to M2.2, and simplify the zoom ladder. One unrelated defect in the M1 converter (section 4) should be fixed now.

## 1. Blocking

**B1. The pan mechanism has no geometry.** Section 3 option B says "a pan shifts the plane base and copies the new tiles", but section 1 and section 4.6 describe a plane of 800 x 720 (1,200 words a line) that also "keeps a one-tile ring". Both cannot hold. If the plane is exactly the screen, a base shift reveals whatever memory follows each line (the next lines, then other data); the scan-out has no wrap (the plan lists the toroidal plane as an RTL alternative, not as existing). And copying the plane itself to follow the pan is not affordable: the plan's own M2 budget (12.x table) is 104 MB/s read plus 104 MB/s write for a full-plane shift on top of 104 MB/s of scan-out, i.e. about 310 MB/s against the measured 193 MB/s fill and 118 MB/s random reads (derived from the plan's Tau V numbers; hardware-validated there). Scan-out alone takes 54 percent of the fill rate, so about 86 MB/s remains for everything else.
*Needed:* state the resident window explicitly. The workable shape is an **oversized resident plane** (for example 1,056 x 976 pixels: the screen plus one 128-pixel tile on every side, stride 1,584 words, which `R_VIEW_STRIDE` allows since it only has to be at least 1,200): a pan inside it is only a base-register change at the vertical blank (applied at the next vblank, source: `mmio.h`, M0.2); only the revealed tiles are copied; when the viewport comes within a tile of the resident edge the window must **re-centre**, and the design must say how (a whole-window copy of about 3 MB read and write, about 70 ms at the spare rate, hidden behind a flip, see B2) or that this waits for a toroidal scan-out. The staging area for landed tiles and the black fill for an axis shorter than the screen (a 4,000 x 600 panorama) belong in the same description.

**B2. Tearing and half-tiles are not addressed.** Copying into the plane that is being scanned out shows partial tiles for as long as a copy runs (M1 already shows a picture painting top to bottom while it lands, which is acceptable for an open, not for a pan). SDRAM has room for two resident windows (64 MB). *Needed:* either a **back window plus a flip** (compose the next viewport in the back window, write the base and stride registers, they apply at the vertical blank) or a rule that a tile is shown only when whole. Note KB-075 (community-reported, medium): output that alternates between two different images frame to frame leaves retention on the panel; a flip that happens once per pan step and then holds a still image is not that, but a design that toggles planes every frame for a still view would be.

## 2. Major

**M1. The card read model is unmeasured and it dominates every number in section 2.** The 1.57 MB/s figure is for a single command from the start of a file (KB-238, community-reported, our hardware test; 4 KB commands 0.96 MB/s, KB-139 about 850 KB/s). A pan reads tiles at **non-adjacent offsets of a 36 MB file**; the docs say the Pocket caches the open file and up to 16 fragments per slot and **discards the cache when the slot switches** (`host-target-commands.md`, docs). A file that is fragmented on the card, or a seek far into a FAT/exFAT chain, can cost more than the transfer, and none of that was tested (KB-238 says: not tested above 128 KB, fragmented files, a second card). *Needed in M2.2:* a read matrix on a real 36 MB file: sequential against random offsets (distance 0 to 30 MB), commands of 16, 48 and 128 KB, a deliberately fragmented copy, and a slot switch between reads. The 600 px/s pan estimate is an upper bound until then.

**M2. A blocking command freezes the input loop.** `slot_read_blocking` cannot be aborted; a 128 KB command is about 83 ms of dead input, and KB-172 (hardware-validated in a sibling project) is the cautionary tale: a blocking job starved the whole main loop for 16 s. *Needed:* tile reads of at most 48 KB (about 30 ms) so the keys are polled between commands; a tile job queue the loop steps, where a direction reversal drops the queued tiles (the command in flight finishes); and the same rule for the Talos copy (a bounded number of row commands per pass). Put the limit in section 4 as a rule with a test.

**M3. The zoom ladder is wrong as written.** Section 4.3 uses a scale of 2 or 1/2, but the fit canvas has an arbitrary scale (a 4,000 x 3,000 photo fits at 0.2, so fit to the 1/4 level is a 1.25x step, not 2x). And beyond 1:1 nothing is gained: the scaler shows each core pixel as 2 x 2 panel pixels, so 1:1 is already the finest detail the panel can show. *Needed:* define the scales explicitly (fit f, then 1/2 and 1:1) and compute the centre-preserving mapping from the two actual scales; keep **at most three stops: fit, 1/2 (only when the source is at least about 1,600 pixels wide), 1:1**; drop the 1/4 level when the step from the previous stop is under about 1.5x. A source no larger than the screen has no zoom at all. This also removes a third of the raw bytes in section 2.

**M4. Raw tile geometry will not survive M3, and the design should say what carries over.** Compressed tiles are small: at 4:1 to 8:1 a 128 x 128 tile is about 6 to 12 KB, so a view of up to 42 tiles is 42 commands that run at the 4 KB-command rate (about 4.2 ms each, KB-238: latency-bound, not bandwidth-bound), about 175 ms before any decode (derived). Two measured points give the per-command overhead: 4 KB in about 4.3 ms and 128 KB in about 83 ms (1.57 MB/s) put it near 1.5 to 2 ms (derived), so the efficient command size is 16 KB and up. *Needed:* choose the tile size and the file order from command economics now, not later: 256 x 256 tiles (a 4 x 4 view of 16 tiles, 192 KB raw, so two commands per raw tile) or **macro-tiles** (a row of 4 tiles stored adjacent) so a horizontal pan step is one coalesced command; keep a per-level `u32` offset table; **reserve layout ids** in the level table now (1 = raw tile-contiguous as designed, 2 = the plan's band-major compressed layout, 3 = reserved) so M3 does not redefine a field M2 shipped. JPEG sources: 128 and 256 are multiples of the 16 x 16 MCU of 4:2:0, so tile edges are legal re-encode boundaries.

**M5. Display depth shows up at 1:1.** The handheld shows 5/6/5 whatever the core sends (KB-237: hardware observation, ramp read back exact in the plane, claim about the cause community-reported; the dock is untested). A fit view averages away banding; a 1:1 view of a sky does not. *Options:* a static ordered dither at the scan-out (a few ALMs, one fit; KB-075 allows only a **static** pattern, never one that alternates per frame), or accept banding. Add a 1:1 gradient test (a smooth sky tile) to M2.5 and decide with a picture in hand; the converter must not dither to 565 (the dock keeps more depth, KB-237).

**M6. No colour management.** ICC profiles are not applied (an M1 limit). Phone photos are often Display P3; shown as sRGB they look oversaturated, and at 1:1 that is what the owner will judge. A host-only fix: convert to sRGB in the converter (Pillow `ImageCms` when an ICC profile is present). Add to M2.1; no hardware involved.

## 3. Minor and suggestions

- **Do option A first, for the 1/2 level.** It needs no Talos and no RTL, and it exercises the pan state machine (viewport rules, clamp, queue, flip) and the card read model (M1 above) before the copy engine is involved. A 2,000 x 1,500 level is 9 MB with 6,000-byte rows; a horizontal pan reads 3x the data it shows, which is acceptable for a proof.
- **Instant zoom feedback, a Pocket-specific idea (untested):** the scaler slot can be switched at run time in about 33 ms (KB-239, community-reported, our hardware test). A second slot at 400 x 360 with a scan-out that reads a 400 x 360 window of the plane would magnify the pixels already in memory (2x) while the next level lands, so a zoom step is never a 1 s black wait. It needs scan-out window registers and an unmeasured switch glitch check: list it as a candidate for after M2.3, not a commitment.
- **Fine pan:** 4 pixels is 8 panel pixels; at 60 Hz a held key gives 240 px/s and a single press jumps visibly. Accept for M2 (decision 2 below). The base register is a word address, so the 4-pixel alignment (six words) is a rule the firmware must enforce and the host test must prove, together with a stride that keeps every line start on a group boundary.
- **Dock:** untested for M2. The dock scales 800 x 720 by a non-integer factor to 1080p; `sharpness` and the pan step look need one dock run. Add to M2.5.
- **Host models understate real cost** (KB-100: a host cycle model was 1.9x optimistic against the real core). Treat every Talos copy time in the design as a lower bound and take the real figure from M2.2.
- **Host tests to add in M2.1:** (1) the tile set of a viewport against a brute-force pixel coverage for random viewports and levels; (2) no viewport inside the resident window ever shows a pixel that has not landed; (3) the zoom mapping keeps the centre within 4 pixels and the round trip is stable; (4) the 4-pixel alignment of the base for every clamped position; (5) the 48 KB command limit and the queue's drop on reversal.

## 4. A defect in the M1 converter found while checking M1 above (not an M2 matter)

`tgy_convert.py` copies the picture's file name into the card path. KB-041 (hardware-validated in a sibling project on an exFAT card: every path with a byte of 0x80 or more fails the core-issued open, NFC and NFD alike) means such a picture would be listed in the grid and then fail with `OPEN FAILED`. Confirmed in this tree: `café 中文.jpg` becomes the card path `Assets/tau_gallery/common/photos/café 中文.tgy`, 8 bytes at 0x80 or more. The folder test written today (B-1017) even asserts that such a name "survives" in the index, which is only half true. *Fix:* give the card file an **ASCII-only name** (transliterate or replace each non-ASCII character, and add a short hash of the original name when anything was replaced, to keep names unique), keep the Latin-1 display name in the index, and make the folder test fail on any index path with a byte of 0x80 or more.

## 5. Answers to the design's four open decisions

1. **Tile levels with a Talos copy, with the geometry of B1 and B2 and a gate:** yes, but pick it only after M2.2 has measured the copy and the card read model; build the pan state machine first on option A (half level). Fall back to a toroidal scan-out only if the re-centre stall or the copy is too slow.
2. **4-pixel pan steps for M2:** accept.
3. **Controls:** accept (A fit and 1:1, L1/R1 zoom, D-pad pans, Select + Left/Right previous and next, B back one level). With at most three zoom stops L1 and R1 are enough.
4. **Raw levels as an off-by-default converter option:** yes, and only for sources of at least about 1,600 pixels; never a 1/4 level (M3 above). About 45 MB per photo until M3.

## 6. What the design gets right
It gates RTL on measurement (M2.0 and M2.2) instead of assuming A1 to A4, it reuses the landing path and the level-table fields that exist, it freezes the viewport rules so a sampler can replace the copy, it keeps raw levels optional and prices them, and its slices split host work from card writes cleanly.
