# Whole-core simulation (sim/fullcore) and the other pre-hardware checks

Status 2026-11-12: **built, boots, runs the host protocol and the firmware, and has a golden frame** (issue 026 fixed, B-1072; golden frame B-1073). `make test-fullcore` (about 3 minutes, 1.5 ms after reset exit) ends with `FULLCORE CPU PASSED`; `make test-fullcore-frame` (about 16 minutes, 20 ms after reset exit) compares the screen bit for bit with `sim/fullcore/golden/boot_20ms.ppm.gz`. The golden shows what the firmware has drawn after 20 ms: the title and the first six rows of the first page's thumbnails (the thumbnails are decoded by the CPU one row at a time; the whole page takes much longer than a gate can afford). It is a regression golden for the whole chain (CPU, firmware, bridge, SDRAM, scan-out), not a picture-quality check; it changes whenever firmware speed or drawing order changes, then `make update-golden-fullcore` after looking at the frame (`tools/ppm2png.py`).

## What it is
`python3 sim/fullcore/run.py [--rebuild] [--dir work/fullcore_data] [--maxus N] [--script 0|1|2] [--extra +TRACE]`: `core_top` as it is built for the Pocket (the real VexRiscv SoC, `tau_tgy_unit`, the SDRAM PHY and scheduler against the timing-checked `sim/sdram_chip_model/`, the video scan-out), a model of the Pocket's host in `tb_fullcore.v` speaking the APF bridge protocol of `core_bridge_cmd.v`, in Icarus. Needs `iverilog` and, in `work/quartus_sim_lib/` (git-ignored, copied from `<quartus>/eda/sim_lib/` on the VM; never committed), `altera_mf.v`; the PLL is our own model (`altera_pll_model.v`). `sim/fullcore/prepare.py` makes the source tree Icarus can elaborate: Quartus tolerates use before declaration and power-up-zero registers, Icarus does not (14 declarations are hoisted, registers are zero-initialised, a zero `build_id.ver` is written). Speed: about 50 microseconds of simulated time per second of wall time; the boot (PLLs, loading the 40 KB firmware through the bridge at the Pocket's pace) is 5.7 ms of simulated time = 2 minutes, a video frame is 16.7 ms = 5-6 minutes. Scenarios: 0 run for `--maxus`; 1 a frame every maxus/12 (slow); 2 one frame after `--maxus`. `+TRACE` prints the CPU's fetch and exception state every 100 us.

## What it has shown so far
- The core elaborates whole (every unconnected input is a finding: one, `vblank_rd`, put X into the CPU in the first attempt).
- The host protocol works: status 4 reached, data slot 1 written (the firmware image lands in RAM, verified word by word), "all slots complete" (0x008F), the core's ready-to-run (0x0140) is answered, reset exit (0x0011), video frames are captured (400 x 360, all black so far).
- Three testbench bugs found by running it: a 32-bit overflow of the watchdog time, a loop index shared by name between the video capture and the boot loop, the first scenario waiting for 12 frames of 16.7 ms.
- **The CPU runs the firmware** since B-1072 (docs/issues/026-fullcore-cpu-illegal-instruction.md: Icarus does not evaluate `always @(*)` at time 0, which left the instruction cache's tags X; `prepare.py` turns the CPU's `always @(*)` into `always_comb`). `+RSTTRACE` prints the reset history and the first 400 fetch clocks with the tag RAM's write chain.
- The host model registers the slots that have a fixed file name in data.json (4, 5, 6, 8) from `--dir`, as the Pocket's host does. Slots 4, 6 and 8 have no file in the data directory (the app does not need them for the first page).
- **Golden frame** (`tools/check_frames.py`, host test `sim/test_check_frames.py`): the data directory is written by `python3 sim/fullcore/make_data.py work/fullcore_data` (the six version-1 pictures and the index of `sim/test_gallery_app.py`, fixed seeds; reproduces the earlier folder byte for byte). `sim/fullcore/golden/boot_20ms.json` records the SHA-256 of every input file and of the firmware image; a mismatch is printed as a note beside the frame result, so a changed input is not mistaken for a behaviour change. On a difference the checker prints the pixel count, the bounding box and the first pixels, and writes `work/fullcore_frames/golden_diff.png`.
- Found while building it, both host-model or simulator artefacts, none a design bug: (1) the host wrote the words of a target read 3 clocks apart; the core's loader takes bytes into a 4-word FIFO at the system clock, so words were dropped, the index header read as X and the firmware looped printing an error: now 40 clocks a word like the firmware load (`+WRITEPACE=n`, 3 is the golden's mutant); (2) the settings register file `set_reg` (a logic-style array that Quartus powers at 0) was X, the firmware computed a theme table address from X and waited on a bus read for ever: `prepare.py` zero-initialises arrays marked `ramstyle = "logic"`. Block-RAM arrays are not initialised.
- Debug switches of the testbench: `+RSTTRACE` (reset history, first 400 fetch clocks, tag RAM chain), `+PCHIST` (the 16 busiest fetch addresses), `+CALLERS +CALLEE=hex` (return addresses of calls to a function), `+DIVTRACE`, `+DBUS` (the CPU data bus once a millisecond).
