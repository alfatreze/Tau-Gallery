# Tau Gallery 1.0: the plan (TGY only)

Status: **draft, 2026-11-13**, written with the owner's decision that 1.0 ships the complete **TGY** path only (the lossy tiled-DCT format drawn by the hardware decoder) and the other formats (TGX lossless, direct JPEG/PNG, camera RAW, container v2) come in 2.0, 3.0 and later. The order of work is the owner's to set; this file proposes one. Evidence in the audit trail (B-1063 to B-1108).

## 1. What 1.0 is
A gallery core for the Analogue Pocket that shows a library of pictures converted on a PC with the Tau Gallery Converter: a grid with thumbnails, a fit view, zoom and pan of any picture the converter can make (tested to 233 megapixels), a map to jump around a zoomed picture, a details page, settings (resume, theme), Help, Info. The decoder is the hardware TGY decoder in the core (bit-exact in simulation, fitted with margin, run on a Pocket).

## 2. Where it stands (DEV 022 on the owner's card, DEV 023 packaged)
Done and run on a Pocket: grid, held keys, fit view, v1 zoom and pan (smooth since DEV 020), pipeline, Info, details page, settings, themes, library of 56 pictures. Done on the host, not yet on a Pocket: histograms of the picture only (DEV 022), the card-resident tile index (DEV 021, partly tried: the owner's big pictures open), the picture-rectangle fix for the navigator (DEV 023). Converter: format choice, parallel tile coding (2.9x), 4:4:4 zoom levels re-encoded as 4:2:0, wide-gamut JPEGs encoded from the sRGB picture so the colours do not jump on zoom.

## 3b. Zoom levels: stored, computed at run time, or a mix
**What a runtime downscale costs.** A view of 800 x 720 at 1:N built from the 1:1 level has to read and decode every source tile it covers: about (800 N / 128 + 1) x (720 N / 128 + 1) tiles, and the card read plus decode is about 11 ms a tile (DEV 020: read 9 to 11 ms, decode 5 to 6 ms, pipelined). The cost grows with N squared:

| View | Tiles | Time |
|---|---|---|
| 1:1 | 48 | 0.5 s |
| 1:2 | 165 | 1.8 s |
| 1:3 | 353 | 3.9 s |
| 1:4 | 611 | 6.7 s |
| 1:8 | 2,346 | 26 s |
| 1:16 | 9,191 | 101 s |

A Talos downscale (K2) would remove the CPU part of this, not the tile reads and decodes, which are the cost; scaling inside the DCT (decoding only the low-frequency coefficients, as libjpeg does) does not help either: the entropy decode of the whole tile and the card read stay. **So a runtime downscale is usable for 1:2 (about 2 s, drawn tile by tile as they arrive), borderline for 1:3, and not for anything coarser.**

**What stored levels cost.** A level every factor F adds 1/F^2 + 1/F^4 + ... of the 1:1 level's pixels, about +6.7 % for F = 4, +12.5 % for F = 3, +33 % for F = 2, at similar bits a pixel. The world map (19.1 MB) becomes 20.4 MB at F = 4 and 25.5 MB at F = 2; a 102 Mpx photo (25.7 MB) 27.4 or 34.3 MB; the converter's work grows by the same fractions. A stored level opens as fast as the 1:1 level (about 0.5 s for the first view) because it is the same tile pipeline: **no RTL, no new CPU code in the hot path**; the firmware needs several tile-level stops in `zs[]` (the version 0 path already has several stops and the map and the stop conversions already take a scale), a per-level tile index loaded when a stop opens (the card-resident index code already works per level), and the container a level kind for them.

**The mix, and the recommendation.** Store levels at factor 4 by default (the cheap +6.7 %: stops at 1:4, 1:16, ... between fit and 1:1), a converter option for factor 2 ("more levels", +33 %), and cover a gap of 2 or 3 between stored stops with the **Talos enlargement by 2 or 3** that the engine already has (`OP_SBLIT`, used as a preview: soft but instant, replaced by the sharper level when it has loaded). A runtime downscale (K2) stays an option for the 1:2 gap only if the Pocket shows the 2 s view to be worth the RTL; it is not a substitute for stored levels beyond that. Decide the default spacing after seeing the stops on the real screen.

## 4. Decisions (owner, 2026-11-13)
1. **Grid sizes: both, and more.** Square thumbnails (cover crop). One stored thumbnail size (96 x 96, the largest cell) and the grid cell is chosen in Settings: 96 x 96 in 4 x 3, 72 x 72 in 5 x 4, and further sizes (for example 64 x 64 in 6 x 5, 48 x 48 in 8 x 6) made by **scaling the stored thumbnail down with the Talos engine's scaled blit** (`OP_SBLIT`), so no extra data in the file. Corner radius: not given; proposed 8 px, set by a constant and judged on the screen.
2. **Folders: one level** for now.
3. **Details: several pages**, a small clear page indicator at the top (for example `1/3` and dots), left and right turn the pages, **no empty fields shown** (a row with no data is not drawn; a page with nothing is not offered).
4. **Converter: the app is the main tool, and the other methods stay** (command line, the library) since they exist. The aim is **the most efficient tools**: first the cheap wins (header checks before the slow read, parallel tile coding: done; optional `jpeglib` for the JPEG read, measured 19 to 75 times faster, with the pure-Python fallback), then a compiled helper inside the app if measurements say it is worth it.
5. **Name: Tau Gallery**, id built the way the other Tau apps' are: core `alfatreze.Tau Gallery`, platform `tau_gallery`, numbered builds `alfatreze.Tau Gallery DEV NN` (this is what `dist/` already holds). **1.0.0 is the first public version.** The developer logo (the core's `icon.bin`) was wrong (a placeholder picture icon): it is now the alfatreze author icon, converted with `tools/convert_pocket_art.py author`. A better core image (the platform artwork) is wanted before release; the placeholder stays for now.

## 5. Risks
- **RAM**: about 2,000 bytes of margin on the 128 KB link (DEV 023). Folder tables and details strings need RAM; plan to reclaim it (the 32 KB zoom index buffer is shared with boot already; the Info and pages code can share buffers).
- **Format change late**: B changes the index and the converter and the firmware together; do it once, early, with a version field, then freeze.
- **The fit**: any RTL change restarts G, so the RTL (package K) is decided first and built as ONE batch; B, C and D need none and can run in parallel with it. Firmware that uses a K block needs its register interface specified early; every K candidate has a software fallback so the firmware does not wait on it.
- **Untested hardware paths**: the Dock, other cards, 1,000 pictures. H should start as soon as DEV 023 is proven, in parallel with B and C.

## 6. Suggested sequence
1. Install DEV 023, confirm A on a Pocket (world map, portrait, histograms).
2. B (format) and C (folders, details pages, grid sizes and look) together, behind one format freeze: start with the written format specification.
3. D, then E and J (they do not touch the firmware).
4. K (RTL: the dither first, then the candidates the owner picks) in parallel with B, C and D: specification, reference models, mutants, probes, whole-core simulation; then ONE fit batch with several seeds (G) once K is frozen; H as cards and a TV are at hand.
5. I, then F, then a release candidate that gets a full Tier C sweep (`CLAUDE.md` section 4).
