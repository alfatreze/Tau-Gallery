# Decision note 2026-11-10: compressed formats first, whole picture resident in SDRAM, pan and zoom from memory

Owner decisions (2026-11-10): (1) tuning the raw-tile pan from the card is not worth more effort, because the goal is to load the owner's own format (TGY, then TGX) and also JPEG and PNG directly, even if the load is slower; (2) the format work comes first, TGY before TGX; (3) the compressed picture is streamed into SDRAM (PSRAM as a cache at most) once, and pan and zoom decode from memory instead of streaming from the card. This note records what that means. Plan sections: 6.5 (TGY), 6.6 (TGX), 8 (milestones, M3 and M4); M2 design: `docs/M2_DESIGN.md`.

## 0. Priorities (owner, 2026-11-10)
1. **Essential, the critical goal: TGY and TGX in hardware** (both decoders, and the host encoders that feed them). TGX is no longer "optional later": it is part of the essential goal, TGY first.
2. **Nice to have, for the user's quality of life (reading straight from a card): JPEG direct and PNG direct**, even if their load is slower than a converted file. They follow the hardware TGY and TGX work and reuse its pieces where they can (JPEG shares the TGY back end; PNG is a separate sequential engine).
3. **Much later: camera RAW** (loading raw files from a camera). Not planned here beyond this line.

## 1. Vocabulary (what is meant, so the code and the plan agree)
- **TGY**: the native lossy photo format. Tiled (128 x 128, independent tiles), a JPEG-class DCT with quantisation and an adaptive binary range coder; resolutions 1/8, 1/4, 1/2, 1/1 by DCT-domain scaling at no extra storage; band-major layout (DC, then low AC, then high AC) so a coarse view is a short contiguous read. JPEG sources are recompressed from their coefficients (no added loss); other sources are encoded once at a preset (q95, q92 4:4:4 default, q88 4:2:0). Decoder: range decoder, dequantise, IDCT, colour, chroma upsample.
- **TGX**: the lossless tier for screenshots, text and graphics (where DCT rings): predictor plus context plus adaptive range coding of the residual (the same range coder). Chosen per tile by the mode byte of the same container. Part of the essential goal (section 0), built after TGY.
- **The container** (what the files are today): `.tgy` files hold the header, a thumbnail and levels whose payload mode is RAW (mode 0). TGY and TGX payloads are later modes of the same container; the extension and the codec share the name `TGY`, and the docs say "TGY mode" for the payload.
- **JPEG direct** (plan M4): baseline and progressive, sharing the TGY back end, only the entropy front end differs. **PNG direct**: the plan (section 6 table, line "PNG") had it as "import through the converter; an on-device inflate and unfilter engine is optional and late"; the owner decided 2026-11-10 that it is wanted, as a nice to have after TGY and TGX. It is a separate engine (inflate and the five PNG filters, a sequential stream): the whole picture is decoded once into raw pixels in SDRAM and panned from there (a 12 MP picture is 36 MB, so a very large PNG needs a decode into tiles or a size limit, to be decided with the first measurements).

## 2. Why a resident compressed picture
The raw pan is limited by the card (about 38 ms for a 48 KB tile, B-1024 to B-1035). With the compressed file resident in SDRAM the card is read once per picture (the DC band first, so a coarse picture appears early and refines while the rest loads), and every pan and zoom step reads SDRAM; the limits become decoder throughput and SDRAM bandwidth. The tile cache API (request `(image, level, tx, ty)`, get a slot or pending) does not change, only its backing store. This needs a compressed format: a raw 1:1 level of a 12 MP photo is 36 MB.

## 4. What stays and what goes
- **Stays (format-independent):** the viewer and landing path, the container and index, the resident window and follow rule, the loader bar, the map, the settings and screens, the Talos tile copy (still how decoded tiles get into the plane).
- **Goes or waits:** tuning built around the raw 48 KB tile cost (pan cap per frame, window sizes), the card-streaming pan as the final design (it stays as the RAW fallback), the hardware map overlay (little value before the decoder exists).

## 5. Work order
1. **Host, no hardware** (revised by the codec review, section 11): (a) the range coder reference, done; (b) a **JPEG coefficient reader** (baseline and progressive Huffman, the five test photos are progressive), because the entropy model must be measured on the ORIGINAL quantised coefficients, not on re-quantised pixels; (c) the context-model measurement with tile-reset contexts (section 11, D2); (d) the TGY encoder and reference decoder, quality presets, the exact size and speed numbers.
2. **SDRAM-resident store (firmware and RTL interface):** whole-file landing in 128 KB commands (the largest measured), the band-major progressive load, and the tile cache API backed by SDRAM; measure reads above 128 KB and fragmented files.
3. **RTL decoder** (range decoder front end, dequantise, IDCT, colour, upsample), on the shared port structure (the plan: a write mux with the landing path); two-seed fit; M10K budget (264 of 308 used by the stripped M0 core, 86%).
4. **TGX** (host encoder and reference decoder with the same range coder, then the hardware decoder): essential.
5. **JPEG direct** on the TGY back end (M4), then **PNG direct** (inflate, filters, a decode into SDRAM): nice to have, in that order. Camera RAW much later.

**Software PNG inflate (nice to have) is unmeasured.** A PNG decode on the CPU is inflate (Huffman) plus the five filters over the whole raw picture (12 MP is 36 MB). The results decide whether a PNG or JPEG path stays in software (with the clock and RAM options above as levers) or gets an RTL block after TGY and TGX.

## 8. Main RAM budget: how small can the CPU's RAM be (2026-11-10, link numbers measured, saving estimated)

**What a block costs (measured earlier in this project):** shrinking the main RAM from 256 to 192 KB freed exactly 64 M10K blocks in real fits (`docs/RAM_SHRINK_192K_PLAN.md`: 299 of 308 used became 235 of 308), so **one M10K block per KB**. The current stripped core therefore spends about 192 of its 264 blocks (73%) on the main RAM (derived, not read from a fit report: the VM was unreachable when this was written). The decoder will need tens of blocks, and everything else together is about 72.

**What the gallery firmware needs (measured from today's `APP=gallery` link, `work/diagnostics/gallery-app/fw2.elf`):**

| Item | Bytes |
|---|---|
| code, read-only data, initialised data (the ROM) | 35,904 (text 32,244, rodata 3,373, data 284) |
| zero-initialised data (bss) | 14,060 |
| image end (`_image_end` 0xC330) | 49,968 |
| `_min_free` | 1,024 |
| the 4 KB landing zone (`_tag_size`) | 4,096 |
| stack (`_stack_size` 0x1400) | 5,120 |
| compressed-audio ring (`_ring_size` 0x6000), **reserved by `link.ld` but unused by the gallery** | 24,576 |
| **needed without the ring** | **60,208 (58.8 KB)** |

The linker still reserves the 24 KB ring that only the audio player used; dropping it is free.

**Options (one block per KB):**

| Main RAM | Spare after the needs above | Blocks freed (of 192) | Blocks used afterwards | Notes |
|---|---|---|---|---|
| 192 KB (today) | 132 KB | 0 | about 264 (86%) | |
| 128 KB (one 32,768-word region) | 68 KB | 64 | about 200 (65%) | simplest, no split |
| **96 KB (16,384 + 8,192 words)** | **about 37 KB** | **96** | **about 168 (55%)** | the same 2:1 split shape as the proven 192 KB (32,768 + 16,384); room for the decoder's driver code, TGX tables and growth |
| 64 KB (one 16,384-word region) | about 5 KB | 128 | about 136 (44%) | fits today's firmware but leaves no room to grow |

**Recommendation (revised 2026-11-10 after the owner asked "why not 128"): 128 KB.** It frees 64 blocks (about 200 of 308 used, 108 free) against 96 KB's 96 (about 168 used, 140 free), but it is **one power-of-two array** (`WORDS_B=0`, the structure the original core always used), so it avoids the two-region inference risk of KB-058 altogether, needs no new split logic and no new address-select path, and leaves 68 KB of RAM for software work: the Huffman and window tables of a software PNG or JPEG path, line buffers, the decoder's driver and TGX tables. The plan's TGY decoder is estimated at 30 to 50 M10K blocks (a 70-block candidate was the one rejected as too big), so 108 free blocks cover it with room for the sampler or overlay; 96 KB is the fallback only if the decoder's measured block count turns out well above 70, and 64 KB stays a trap. Because the main RAM is one parameter, the choice can be revised after the first decoder fit.

**What has to change (none of it done):** a macro beside `TAU_RAM_192K` in `tau_soc.v` (for example `TAU_RAM_96K`, parameters `WORDS_A=16384`, `WORDS_B=8192`, `RAM_AW`), a new `CORE_VERSION` revision so firmware linked for another size refuses it (the pairing rule B-245: a firmware linked for more RAM than the core has corrupts silently), a `link.ld` variant (RAM length 0x18000, ring size 0 for the gallery) and the matching `P2_CORE_VERSION` in the firmware build, the `tau_main_ram` testbench with the new split, a Quartus **synthesis** check first (the documented risk in `tau_main_ram.sv`: a different restructuring once made Quartus fall back from M10K to logic; a 2:1 split like the proven one should be safe but must be checked), then a two-seed fit (about 1h10m, the owner's yes) and a Pocket boot.

**Unchecked:** anything else that assumes the RAM size (the loader's size check for `tau.rom`, the SoC simulation's RAM model in `sim/make_soc_sim.py`, the 0xC0000000 uncached alias and address decoding, the watchdog's jump buffer), and whether the fitter packs the smaller array as one block per KB again.

**The size rule, checked 2026-11-10 (the "modulus"):** each RAM array must have a power-of-two depth. The source says so (`tau_soc.v` line 41 and `tau_main_ram.sv`: a single 49,152-word array once pushed the Fitter into logic instead of M10K, "Fitter requires 3621 LABs ... device contains only 1848"), which is why 192 KB is two arrays of 32,768 and 16,384 words per byte lane. 96 KB (24,576 words) is not a power of two either, so it is built the same way: **16,384 + 8,192 words**, both powers of two, region B no larger than region A (the module's precondition), and one address bit (bit 14) tells the regions apart with no subtractor. That is the 192 KB shape halved, and `tau_main_ram` already takes it as parameters (`WORDS_A=16384, WORDS_B=8192`, `AW` of at least 15; `RAM_AW` is 16 today). The instantiation in `tau_soc.v` hard-codes the 192 KB numbers, so a new macro branch is needed, and the address decode, the loader address and the version interlock around line 1027 need the same branch. The real risk is inference, not the arithmetic: the same file's history (B-225 to B-227) and skill entry KB-058 record that a two-region split can make Quartus fall back from M10K to registers when the read is written as a ternary across two multi-array concatenations; the shipped module avoids that shape (a plain registered read per region, then a byte mux), and the 192 KB version of it is fit-proven, so a 2:1 split with half the depth should infer the same way, but only a synthesis run proves it. Skill entries consulted: KB-143 (M10K is 10,240 bits, 308 on this device; check the fitter's RAM summary for block type, width and depth), KB-058, KB-052.

|---|---|---|---|---|---|
| detailed photo | 40,539 (1.21x) | 3.05 M cycles (62.1 per byte) | 2.49 M cycles (50.7) | **112.8 cycles** | 83 ms |

Extrapolated to whole pictures at 66.67 MHz (the same cycles per byte; **estimate from a 49 KB sample**): a 12 MP photo is 36 MB of raw bytes, so about **61 s** at 112.8 cycles per byte (a 21 MP photo about 108 s), a screenshot-like picture about 25 s per 12 MP. This is the best case: 0-wait RAM, the whole picture in RAM, no SDRAM traffic; a real run writes the output to SDRAM through uncached accesses and would be slower. **The earlier guess of "many seconds" was about ten times too optimistic.**

Reading it: the row filters cost almost as much as inflate (Paeth dominates a photo: 125 of 128 rows were Paeth in the photo crop), the code is not optimised (a 2x gain is plausible, unmeasured), a 100 MHz CPU would give 1.5x, and a CFU does not fit the problem. A software PNG path would make a 12 MP photo take on the order of a minute: acceptable only for small PNGs or as a last resort. The levers, in order of value: an **RTL unfilter** (a streaming Paeth unit is tiny), an **RTL inflate** (Huffman decode plus a 32 KB window, about 4 M10K, the plan line 631 lists it) which is the optional late engine of plan section 6.6 table, a size limit with a clear message for large PNGs, and a progressive display (Adam7 interlaced PNG gives a preview).

## 10. The entropy coder reference (2026-11-10): the TVC range coder, bit-exact
The plan's "reuse" of the TVC range coder was checked against the source: the coder is specified in Tau codecs (`docs/TVC_BITSTREAM_V0.md` section 3, `tau-video/src/tvc/range.rs`): 32-bit `range` and `code`, **15-bit probabilities** (initial 16,384, adaptation shift 5), bypass bins, normalise while range < 2^24, a 5-byte flush, zero bytes past the end on decode. `tools/gallery/tvcrc.py` reproduces it (encoder and decoder). `make test-tvcrc`: 10 tests (round trips of context and bypass bins, probability bounds, extreme skew, carry runs, zero padding, the carry branch with the low 32 bits at 0xFF, fixed regression vectors), **13 of 13 mutants killed** (a mutant that hangs the coder counts as killed after 5 s), and `sim/cross_tvcrc.py`, which builds a throwaway Rust crate from a copy of the Tau codecs file and compares **47 sequences bit for bit** (encoded bytes and decode), all identical. The cycle cost of this coder on the CPU is the 31.6 cycles per decision measured in plan 12.11 (an LZMA-style 11-bit coder; the TVC coder is the same shape with 15-bit probabilities, so the number is close but not identical). The hardware decoder and the firmware's C decoder must reproduce `tvcrc.py` exactly; the next piece is the TGY symbol layer (binarisation and contexts for DC, AC and the tile header), then the encoder and reference decoder.

## 12. The JPEG coefficient reader (2026-11-10, done, host-tested)
`tools/gallery/jpegcoef.py` returns the quantised DCT coefficients exactly as stored: baseline, extended-sequential and progressive Huffman JPEG (all five test photos are progressive 4:2:0, Y sampled 2 x 2), 1 or 3 components, restart intervals, odd sizes; arithmetic-coded, 12-bit, lossless and hierarchical files raise `ValueError`. `make test-jpegcoef`: 13 tests (the dequantised, inverse-transformed output reproduces what Pillow (libjpeg-turbo) decodes: luma within rounding for baseline and progressive, 4:4:4 and 4:2:0, chroma on its own grid; the DC coefficients equal Pillow's 1/8-scale decode; **baseline and progressive encodings of the same noisy 4:2:0 picture hold identical coefficients, and restart intervals change nothing**; damaged and unsupported files raise) and **14 of 14 mutants killed**. On the real 2560 x 1705 progressive photo: read in 3.0 s (faster than the "about a minute for 20 MP" guessed), luma error against Pillow mean 0.31, max 8.3 over 4.4 M pixels (coefficients correct on real data); 29.8, 28.4 and 23.6 nonzero AC coefficients per Y, Cb and Cr block. `jpegtran` IS installed (`/opt/homebrew/bin/jpegtran`, with arithmetic coding); its arithmetic-coded size of each photo, measured 2026-11-10 (the starting figure the TGY model must beat): c6227db76b6e 2,512,188 of 2,551,548 bytes (0.985), 56623f02e42e 2,349,384 of 2,486,350 (0.945), 3b5ec3a7fe05 6,095,482 of 6,590,478 (0.925), b586d89ba3ee 3,290,426 of 3,642,324 (0.903), 21bda4d32df4 2,881,173 of 3,177,854 (0.907): mean 0.933, the plan's figure, now measured here. Next: the context-model measurement of decision D2 (a binarisation and context set, coded with the TVC coder in tile-reset streams, round-trip checked, compared with the original size and the static limit).

## 13. The context-model measurement, first results (2026-11-10, decision D2; measured)
**Setup.** `tools/gallery/tgymodel.py` is a first-cut TGY symbol layer over the TVC coder, written once and run as cost counter, real encoder and decoder (`make test-tgymodel`: 10 tests; every variant round-trips tiles bit for bit through the real TVC encoder and decoder, the ideal cost agrees with the real stream within the 5-byte flush). Per block, in zigzag order: the DC difference to the left (else above) block of the tile, the index of the last nonzero AC (a 6-bit tree), a significance flag for each position before it, a greater-than-1 flag, an Exp-Golomb remainder and a bypass sign; 13 position groups; one stream per 128 x 128 tile (256 Y blocks and 64 + 64 chroma blocks), contexts reset per tile. `tools/gallery/model_measure.py` cuts a lossless 1024 x 1024 crop (jpegtran, tile aligned, so the coefficients are exactly the original's) from each of the five photos (320 tiles) and codes the same coefficients with jpegtran as baseline Huffman, progressive Huffman and arithmetic coding, and with the model variants. Sizes in bytes, total over the five crops (ideal code length plus 40 bits a tile; the file headers of the JPEGs are about 600 B each):

| Coder | Bytes | Ratio to progressive Huffman |
|---|---|---|
| JPEG baseline Huffman (optimised) | 1,927,670 | 1.038 |
| **JPEG progressive Huffman** (what the originals are) | 1,857,387 | 1.000 |
| JPEG arithmetic (`jpegtran -arithmetic`) | 1,787,810 | 0.963 |
| model, TVC as specified (shift 5), no neighbour contexts | 1,775,644 | 0.956 |

**What it says (first model, five photos, 1024 x 1024 crops, one quality range of web photos):**
1. The simple tile-independent model with the TVC coder as specified is already about 4% smaller than the progressive Huffman originals and slightly better than JPEG arithmetic coding; the count-based rate brings it to **6% smaller** (0.940). That is **below the 7 to 15% estimate of D3**, at the bottom of the range of "better than arithmetic" and far from the 20 to 22% of Lepton-class recompressors (recalled). The gain over the originals is modest; the value of TGY for JPEG sources stays random access and hardware decode.
2. **D1 confirmed in part:** the count-based rate is worth **1.7%** over the fixed shift-5 rate (0.940 against 0.956). **Trained priors are worth 0.1% at most** (0.941 and 0.940): not worth a table in the header or a context-initialisation path in the decoder; the count-based rate already learns fast. Drop priors from the format unless a richer model changes this.
3. **Neighbour contexts, as defined here (the same position in the left and above blocks), give nothing** (0.941 against 0.940 with the count rate, and 0.5% worse with the fixed rate, where more contexts cost more to learn). A neighbour-free model needs no coefficient line buffers in the decoder: a hardware saving.
4. **Not measured and not excluded:** the richer modelling that gives Lepton its size: the count of nonzero coefficients coded first and used as the context of the significance flags, DC prediction from pixel gradients across block edges (not possible across tile edges, but possible inside a tile), prediction of the first row and column of each block from the neighbours' pixels. These are the next measurements; they cost decoder state, which is the trade-off to evaluate (each is a context or a small predictor, not a mixer).
5. **Hardware throughput (measured decision counts, count-based variant):** per tile 24,000 to 89,000 context-coded decisions (mean 42,000) and 7,000 to 33,000 bypass bins (mean 14,000), 2.8 to 11.7 KB (mean 5.5 KB) of compressed data, 0.61 to 0.79 bits per decision. At 3 clock cycles per decision (an estimate) a mean tile takes 1.3 ms at 100 MHz (the densest 2.7 ms plus bypass bins), so a screen of 36 tiles is about 50 to 100 ms in one lane: the entropy decoder is not the bottleneck of the pan, the card and the Talos copy are.

## 14. Richer contexts, measured (2026-11-10): small gains, and where the bits go
`tgymodel.code_block2` adds, as options, the count of nonzero AC coefficients coded first and used as the context of the significance flags (`nz`; the remaining count also makes the last flags implicit), the magnitudes of the two already-coded neighbouring coefficients inside the same block as context (`local`), the median of left, upper and left + upper - upper-left as the DC predictor (`dcmed`), and the neighbouring blocks' nonzero counts as context of the count (`nznb`). `make test-tgymodel`: 14 tests, **all 16 option combinations round-trip bit for bit through the real TVC encoder and decoder** on synthetic, extreme and real tiles. Same five lossless crops (320 tiles), count-based rate, `tools/gallery/model_measure2.py`; bytes over the five crops, ratio to the progressive Huffman crops (1,857,387 bytes):

| Variant | Bytes | Ratio |
|---|---|---|
| old model (last index tree, left/above DC) | 1,746,393 | 0.940 |
| **+ local (neighbouring coefficients in the block)** | **1,732,402** | **0.933** |
| + dcmed | 1,743,679 | 0.939 |
| nz count | 1,745,434 | 0.940 |
| nz + neighbour counts | 1,746,492 | 0.940 |
| nz + local | 1,743,405 | 0.939 |
| nz + local + neighbour counts | 1,744,465 | 0.939 |
| nz + local + dcmed | 1,740,691 | 0.937 |
| nz + local + dcmed + neighbour counts | 1,741,751 | 0.938 |

**Where the bits go** (the `+ local` model, 1,730,805 bytes; measured): magnitude exponent 22.4%, significance flags 18.9%, greater-than-1 flags 9.0%, magnitude top mantissa bit 8.4%, last-index tree 3.9%, DC (all four symbols) 4.1%, and **33.3% raw bypass bits: the AC signs 16.1% and the lower mantissa bits 17.2%**.

**What it says:**
1. The best variant is `+ local` alone at **0.933** (6.7% smaller than the progressive Huffman originals). The nonzero-count scheme, the DC median predictor and the neighbouring-block counts add nothing on top (the nz count even loses 0.1 to 0.2% to the last-index tree here), so the **simplest model wins: the last-index tree, left/above DC, the local-energy context, the count-based rate, no priors, no neighbour-block contexts**. In hardware it needs only the 64 coefficients of the block being decoded (which the dequantiser and IDCT hold anyway): no line buffers, no tables.
2. **The ceiling of context modelling on this data is low:** one third of the stream is raw bits that no context removes (signs and the lower mantissa bits), DC is only 4%, and the flags and exponents already sit near the static limit. The remaining lever known from the literature (recalled, not measured here) is predicting the **signs and magnitudes of the first row and column of each block from the neighbouring blocks' edge pixels** (Lepton's edge prediction); it needs the neighbour block's decoded pixels (the IDCT's last row and column) and is not possible across tile edges. Its gain is unknown here and probably a few percent; it is the one remaining experiment, and its hardware cost (an extra row and column buffer per block row) must be weighed against that.
3. **The 20 to 22% figure is therefore out of reach for a tile-independent, mixing-free design** on these photos; the realistic expectation for JPEG sources is **6 to 7% smaller than a progressive Huffman original (measured), about 3% smaller than arithmetic JPEG**, with random access and a hardware-decodable stream as the real gain. For pixel sources the same coder and model are applied to coefficients our own encoder quantises, where the lever is the encoder (quantisation matrices, dead zone, rate-distortion optimised quantisation), not the entropy model.
4. Recommended **TGY v0 symbol layer**: the `+ local` variant of `tgymodel.py`. Decisions D1 (count-based rate kept, priors dropped) and D3 (expectation 6 to 7%) are confirmed by measurement; the symbol layer is frozen only after the edge-prediction experiment, or after the owner decides it is not worth it.

## 16. Reconstruction frozen (2026-11-11): bit-exact with libjpeg-turbo, tile-local chroma upsampling (decision D4 settled)
**What was built.** `tools/gallery/tgy_recon.py`: dequantisation, libjpeg's `jpeg_idct_islow`, its range limit (including the wrap), its integer YCbCr to RGB tables, its h2v2 fancy upsampling (with the box fallback for planes no wider than 2 samples), tile splitting with partial tiles at the edges and reassembly. Normative text: `docs/TGY_RECONSTRUCTION_V0.md`; vectors: `docs/conformance/tgy_recon_v0_vectors.json` (IDCT cases with saturation and wrap, colour triples, upsampling cases, three whole pictures with SHA-256 under both profiles). `make test-tgy-recon`: 10 tests + 4 vector tests, **18 of 18 mutants killed**.
**Measured results.**
1. **The reconstruction equals libjpeg-turbo (Pillow) bit for bit** on baseline and progressive JPEGs, 4:4:4, 4:2:0 and grey, sizes from 2 x 2 to 300 x 200 and odd shapes, noise at quality 5 and 100 (saturation and the range-limit wrap), and a real photo crop; it was exact on the first run.
2. **The whole chain is lossless and pixel-identical:** JPEG coefficients -> 128 x 128 tiles (partial tiles at the edges) -> TGY symbol layer v0 streams -> decoded -> reassembled coefficients (identical) -> pixels (identical to libjpeg-turbo's decode of the original file), tested on a 4:2:0 progressive picture, a 4:4:4 picture of odd size and a real photo crop.
3. **Decision D4 settled: the normative TGY profile upsamples each tile's chroma on its own** (the tile's border samples replicated), so a tile needs nothing from its neighbours. It equals libjpeg's whole-plane result except in the outermost row and column of luma samples of each tile (tested exactly), and everywhere for single-tile pictures and for 4:4:4 and grey. Measured on the five 1024 x 1024 crops: 0.2 to 2.2% of the pixels differ, by 1.7 to 3.7 levels on average where they do (maximum 29 on the most saturated crop), 55.2 to 73.7 dB PSNR. The alternative (carrying neighbour samples in each tile) would cost about 27% more chroma bits (estimate: 17 extra chroma blocks per 64) or a whole-plane pass; the libjpeg profile stays available to decoders that hold whole planes (direct JPEG, M4).
**What is still undefined for TGY** (the next specification parts): the container (tile offsets, lengths and CRC, the band layout, the fit level), the converter from JPEG coefficients and the encoder for pixel sources (quantisation tables, rate-distortion optimisation), TGX's symbol layer, then the firmware C decoder and the RTL decoder held to the vectors.

## 18. The C decoder of the symbol layer (2026-11-12, resumed session): the firmware reference
`fw2/gallery/tgy_dec.c` and `tgy_dec.h`: pure C99, no libc, no allocation; the decoder state is a `tgy_dec_t` of 3,766 bytes (1,250 contexts of a 16-bit probability and an 8-bit count, plus the range decoder), the code is **2,132 bytes** (rv32im, -Os, measured). It is **total**: any byte string decodes to something in bounded time (an Exp-Golomb exponent above 15 stops the tile and sets the error flag, values saturate to int16), so a corrupt tile can neither hang nor write outside its buffer. `make test-tgy-dec-c`: all 9 frozen conformance vectors and 60 more random tiles from the reference encoder decode bit for bit (also with the trailing zero bytes of the stream dropped, as the spec allows), 4,000 fuzzed streams (all-ones, all-zeros, random; random lengths and shapes) terminate with no AddressSanitizer or UBSan report (1,110 of them are flagged impossible), the C tables and context offsets equal the conformance file's constants, the engine saturation points equal the reference's, and **23 of 23 mutants are killed**. Two corrections on the way: the first mutant run showed that a rate table entry off by one is not found by random vectors (a decision changes about once in thousands of tiles), so the tables are now compared directly with the conformance constants; and the clamp and zero-padding mutants needed an engine saturation check and trimmed-stream decoding to be caught.
Not done: the RTL decoder, wiring the decoder into the gallery firmware (it needs a tile buffer: a 4:2:0 tile of 384 blocks is 48 KB of int16 coefficients, so decode block by block into the IDCT, which is the next design step), TGX, the intermediate zoom levels, the folder index for container v1, and any Pocket run.
