# 026: the whole-core simulation: the CPU takes an illegal-instruction exception at address 0 and loops

Opened 2026-11-12 (owner: Abel Santos; worked by Claude). Not in `make test` or `make gate` for exactly this reason (CLAUDE.md rule 5).

Reproduce: `python3 sim/fullcore/run.py --rebuild --dir work/fullcore_data --maxus 300 --script 0 --extra +TRACE` (about 12 minutes). Facts from the trace after reset exit (5.72 ms): clock running (66.7 MHz), `rst` 0, RAM words 0..3 equal the firmware image (`00020117 00010113 00000297 06428293`), `mcause` = 2 (illegal instruction), `mepc` = 0, `mtval` = X, `mtvec` = 0 so every trap re-enters address 0; the CPU's wishbone instruction bus (`iCYC`) never asserts, `iADR` stays X, the data bus never asserts; `lineLoader_valid` 0, the instruction cache flush has finished (counter 0x80).
Hypotheses, none checked: (1) the instruction at 0 was fetched (as zero or X) before the loader finished and the instruction cache or the fetch pipeline kept it; on the Pocket the CPU is held in reset until the host's reset exit; here `rst` may deassert earlier; (2) an X in a register Quartus powers up at zero that the zero-initialisation pass of `prepare.py` does not reach (the CPU's decode ROM or the cache tags are memories); (3) the fetch path of this build (PSRAM_IFETCH, the 128 KB RAM option) is fed through something the model does not drive. First step: print `dut.u_soc.rst` from time 0 and the first fetched word; compare with `tb_tgy_soc.v` (same CPU, runs the same firmware class correctly under Icarus).
