## 2. Decisions taken (change any of them cheaply now, expensively after M1.4)

1. **The fit view is one contiguous read.** The M1 level of a picture is the "fit canvas": the picture with its EXIF orientation applied, scaled to fit 800 x 720 (never enlarged unless `--upscale`), centred on black, stored exactly as the viewer plane wants it (rows of 800 pixels of R, G, B bytes, 2,400 bytes a row, 1,728,000 bytes). Opening a picture is one data-slot read of that run with the landing window set to the plane base: about 1.1 s at 1.6 MB/s (measured rate for large commands), no copy, no tile placement. The plan's tiles (128 x 128, tile-contiguous) are for zoom and pan (M2): they need strided placement into a plane, which is Talos's unverified reach (A1 to A4), and M1 does not wait for that. The level table of the file has `layout` and `mode` fields so tile levels and TGY payloads are added later without a new format; a reader rejects a level it does not know.
2. **A picture is ONE file, 4 KB aligned inside.** Header (64 bytes), level table, the 96 x 72 RGB565 thumbnail at 4,096, the canvas at 20,480. File size 1,748,992 bytes for every picture in M1 (the canvas is always 800 x 720), so 100 pictures are 175 MB.
3. **The folder index is the library slot.** `tau-library.tdb` (a TGIX v0 file: header, 160-byte entries with the path on the card, a Latin-1 display name, size, original width and height, then the thumbnail atlas, 13,824 bytes each in entry order) is read through data slot 5, whose declared file is `tau-library.tdb`: the converter writes the index under that name (`--index-name`) so no new slot or loader entry is needed. A page of 16 thumbnails is 221 KB contiguous in the atlas: one read.
4. **Pictures are opened by path** with the existing open-by-path command (`slot_open_path`, proven for tracks) on the picture slot (slot 2, renamed "Picture" with the extension `tgy` in M1.3). The path comes from the index.
5. **Pixels stay 8 bits per channel in the file** even though the handheld display shows 5/6/5 (docs/M0_DESIGN.md 6d, skill entry KB-237): the dock may show more, and the stored format should not be the limit. Thumbnails are RGB565 (they are only ever shown in the 565 UI). A dither to 565 in the viewer's last stage stays an option (M0 open item).
6. **The grid is drawn by firmware in UI mode**: 4 x 4 thumbnails of 96 x 72 on the 400 x 360 UI (plan section 7). A thumbnail reaches the screen as 4 KB reads into the tag zone and mailbox writes into the framebuffer (about 30 ms each, 0.5 s a page); a faster path (Talos copy from SDRAM rows) is an M2 matter.
7. **Names:** the display name is the file name without extension, Latin-1 (other characters become `?`), 39 bytes; the card path is **ASCII only** and under 96 bytes (changed 2026-11-09, B-1018: the Pocket's core-issued open fails for any path with a byte of 0x80 or more, KB-041; a non-ASCII character in the file name becomes `_` and a short CRC of the original name is added, so two names never collide; the Latin-1 display name keeps the original text). A path that is too long is not cut: the file is skipped with a clear message and the rest of the folder converts (B-1017).
8. **Orientation and colour:** the converter applies EXIF orientation (all eight) and converts to RGB; ICC profiles are not applied in M1 (sRGB assumed), a known limit.

## 3. File formats (v0)

TGY header, little-endian, 64 bytes: magic `TGY\0`, u16 version 0, u16 header size 64, u32 width, u32 height (orientation applied, original size), u8 channels 3, u8 tile_log2 7, u8 orientation 0 (applied), u8 flags, u32 level count, u32 level table offset (64), u32 thumbnail offset, u32 thumbnail bytes, u16 thumbnail width and height, u32 meta offset and length (0), u32 file size, u32 CRC-32 of bytes 0 to 51, 8 reserved. Level entry, 48 bytes: u32 width, u32 height of the canvas, u16 content x, y, w, h (the picture's rectangle on the canvas), u8 layout (0 raster), u8 mode (0 RAW), u8 pixel format (0 RGB888), u8 kind (0 fit canvas), u32 row stride (2,400), u32 data offset, u32 data length, u32 index offset and length (0), u32 CRC-32 of the data, u32 reserved. The reference implementation is `tools/gallery/tgy.py` (`pack_tgy`, `parse_tgy`, `level_bytes`, `pack_index`, `parse_index`); the tests are the specification of the damage a reader must refuse (bad magic, version, header checksum, size, level checksum, unknown layout, mode or pixel format).

- A card layout for the pictures (`Assets/tau_gallery/common/photos/` by default).
- The first-picture experience: a progress bar while 1.7 MB lands (about 1.1 s), and which key does what (A opens, B back, L1 and R1 page, Left and Right neighbour picture).
- Memory: a plane is 1.7 MB of the 64 MB SDRAM; the next picture can be landed into a second plane while the first is shown (M2 prefetch), the viewer switches by the base register at a vblank.


## 5. M1.6 gallery screens (designed 2026-11-09, owner chose all four: Settings, Controls + Help, Info, Theme)

**Base that stays:** `ui/helios` (beam-aware dirty regions), `cores/view_core.h` (view table with enter, exit, input, draw), `ui/regions.h`, `ui/theme*` with `cores/theme_core.h` and `colour_core.h`, `cores/help_core.h`, `controls_core.h`, `menupages_core.h`, `configure_core.h`, `counters_core.h`, `about_core.h`, and the kept views `settings_view`, `controls_view`, `help_view`, `configure_view`, `appearance`. **What they still include and must lose:** `transport/mp3play.h` (player state), `aout/aout.h`, `meter.h`, `meter_registry.h`, `nowplaying.h`, `xfade.h`, `meterlist_thumb.h`, `halcyon_view.h`, `transport/browser.h` (all deleted). `ui/views.c` is the player's view table and is rewritten for the gallery: views GRID, VIEWER, MENU, SETTINGS, CONTROLS, HELP, INFO.

**Proposed shape (change any of it before M1.6 starts):**
1. Start opens a menu from the grid (the viewer keeps B = back, Left/Right = previous/next). Menu entries: Settings, Controls, Help, Info. Select-Start combos stay free.
2. **Controls and Help** are static text pages (no persistence): the grid and viewer key map and what the status lines mean. Low risk, first.
3. **Info** shows what the firmware already knows: core and CORE_VERSION, ROM build, picture count, index build, the card read counters (`counters_core`), the last open time. First after Controls and Help.
4. **Theme** (colour roles and font of the grid and status lines) reuses `theme_core`; the choice has to persist, so it waits on item 5.
5. **Settings need a persistence design (owner decision).** The kept `settings/settings.c` and `cores/settings_core.h` are the APF register file (`interact_persist.json`) and every field in `sf_table` is a music field (volume, meters, tunes, last played); the Gallery packages declare no persist words (`add_library_slot(persist_words=False)`). A gallery table (theme, font, last picture, sort, slideshow interval) needs its own field list, a layout version of its own, `core.json`/`interact.json` persist words for it, and a package change; the mechanism (publish only when nothing is streaming, never a file write) stays. Persistence is the one item that touches the package and needs a run on a Pocket to prove.
6. Tests per screen, in the style of M1.3: host test of the cores (existing), and the real firmware against the hardware model for each page, with mutants.

**Order:** Controls + Help, then Info, then the settings table and Settings, then Theme. Each slice is one commit and one DEV build.

## 6. M1.6 Settings: the persistence design (2026-11-09; decisions marked OWNER wait for an answer)

**What exists (read from the code, not assumed).** The Pocket saves a core's `interact.json` variables with `"persist": true` into `Settings/<core id>/interact_persist.json`, and the core reads and writes them through a register file: `R_SET_IDX` (0x6C) selects a word, `R_SET_DAT` (0x70) reads or writes it (`fw2/settings/settings.c`). The gallery package already carries the player's 16 persisted variables (ids 10, 11, 12, 15, 16, 20 to 23, 27 to 33; addresses 0x20000000 + 4 x word), copied from the base core by `package_dev_build.py`; their names and defaults are the player's ("(internal) playback", "appearance", "audio", "meters 1", "last played 1" ...). So **the package already has room for gallery settings: no new variable, no new slot, no bitstream change.** Words 0, 1, 2, 5, 6, 8, 9, 10, 11 and 15 are the ones below 16 (the narrow register file reaches them; words 16 and up need the wide-file probe, `settings.c wide_probe`).

**What does not fit the gallery.** `cores/settings_core.h` is a table of 27 music fields (volume, meters, tunings, last track, a legacy layout 0 migration). `settings.c` publishes with that table. Both stay in the tree only until the gallery table replaces them.

**The gallery table (proposal): new `fw2/gallery/gallery_settings.h` (pure) and `.c` (register access).**

| Word (variable id) | Bits | Field | Values | Used by |
|---|---|---|---|---|
| 0 (10) | 30..27 | layout version | 1 (0 = nothing saved) | validity of the whole file |
| 1 (11) | 4..0 / 10..5 / 11 / 14..12 | accent / theme / polarity / font | 0..18 / 0..31 / dark, light / 0..7 | Theme slice (same bit positions as the player, so `theme_core`, `colour_core` and `ui/appearance` read them unchanged) |
| 2 (12) | 0 | resume the last picture | 0 / 1 (default 1) | the grid opens on the last picture shown |
| 5 (15) | 30..0 | last picture: CRC-32 of its path (31 bits) | | resume check |
| 6 (16) | 30..0 | last picture: its index number | | resume position |

**Rules, each with a test:**
1. **Read:** a word is trusted only when the layout version (word 0) is 1; anything else gives the defaults. Every field is clamped into its range (a raw edit in Core Settings, a garbage word or a card from another build cannot select a theme that does not exist or an index past the count).
2. **Resume:** at boot the saved index counts only when it is below the picture count and the CRC of that entry's path equals the saved CRC; otherwise the grid opens on picture 1. A changed library therefore never opens the wrong picture.
3. **Write:** read-modify-write per word (bits that are not ours stay), word 0 last, and only words that changed. Same discipline as `settings.c`.
4. **When (the risk):** an APF save drops the slot's fragment cache and can disturb a card read in flight (`settings.h`: "published only when nothing is streaming"). The gallery has no stream, but it reads the card in bursts (thumbnails, a 1.7 MB landing). So a change is published only when the app is idle: no key for one second and no read started; the last-picture words are published that way after a picture opens, never during the landing.
5. **Core Settings:** the variables are visible in the Pocket's own Core Settings menu; a value changed there is adopted at the next poll (every 0.5 s, as `settings_service`), clamped by rule 1.

**Package change (as first designed; superseded below, none needed).** `package_dev_build.py` for `gallery` and `galleryapp` rewrites the declared variables: names `(internal) gallery layout`, `appearance`, `browse`, `last picture crc`, `last picture index` with gallery defaults (word 0 default = layout 1; word 1 = accent 1 and bit 30 as the player's default; word 2 = resume on), and drops the 11 unused ones. `tools/persist_registry.json` gets the gallery meanings, and **`tools/tau_compat.py` reads `SF_LAYOUT_VERSION` from `fw2/cores/settings_core.h` (line 220): that fact moves to `gallery_settings.h` in the same change as its test (`sim/test_tau_compat.py`)**. This is the dependency that broke when the audio files were deleted: change the tool, the test and the doc together.

**Tests.** Host: pack and unpack round trip of every field at its extremes; defaults; clamping of garbage; the layout rule; the resume rule (CRC mismatch, index too high, resume off); write only what changed with word 0 last; the idle rule (no publish while a read starts or within one second of a key). App test: the hardware model gets the register file (`R_SET_IDX`, `R_SET_DAT`) with a saved state, the real firmware must open on that picture, and a change in the Settings page must appear in the words; mutants for each rule. **Pocket proof, one run:** the Info page gets two rows (SETTINGS LOADS and STORES, LAYOUT), the owner changes a setting, quits the core, starts it again and sees it kept; that proves the APF round trip for the gallery core id (the one thing the host cannot show).

**Slices.** (a) the table, the register access, the package change and the tests, with only RESUME on the Settings page; (b) the appearance selectors and their effect on the grid and status lines (the Theme slice). OWNER: merge (a) and (b) into one slice, because a selector that changes nothing on screen is dead UI, or keep (a) alone first (smaller, proves persistence before the colours).

**Open owner decisions.**
1. Merge Settings and Theme into one slice, or RESUME first? (recommended: RESUME first, then Theme; the Pocket proof of persistence needs only RESUME.)
2. Font choice in v1? The player's fonts are `.tfnt` files loaded into the writable font RAM (`gfx/font.c`, `generated/fonts/`); the gallery build links only the default font. Recommended: no font selector in v1 (3 bits stay reserved in word 1).
3. Slideshow interval, sort order: **not offered**. Sort needs the converter (the index is read in file order and the firmware reads one page at a time); a slideshow does not exist yet. Say so if you want either planned.

**Built (slice a, 2026-11-09): what changed from the design.** (1) **No package change.** The inherited variables' defaults already fit if the resume flag is stored inverted: word 2 bit 0 is "resume OFF" (the player's default of variable 12 has bit 0 clear), word 0's default already has layout version 1. So `interact.json`, the persist registry and the release checks are untouched, and the only compat change is the source of the `persist_layout` fact (`GS_LAYOUT_VERSION` in `fw2/gallery/gallery_settings.h`, in `tools/tau_compat.py`, with `sim/test_tau_compat.py` and `sim/test_install_dev_core.py` still passing). Words 5 and 6 default to the player's mark 0x40000000, which never matches a picture (the index is past the count). (2) The Pocket's Core Settings can move the variables: `gs_hw_service` adopts a change at the next poll (every 0.5 s). (3) Files: `gallery_settings.h` (pure: table, unpack, pack, resume rule, publish rule), `gallery_settings.c` and `gallery_settings_hw.h` (the register file), `gallery_pages.h` (the SETTINGS menu entry and page, the Info row), `gallery_app.c` (boot resume, `last_act` clock, `settings_tick` in every idle loop, the last picture recorded when an open lands).
