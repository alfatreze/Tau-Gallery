# TGY container, version 1 (FROZEN 2026-11-11)

Normative. Reference: `tools/gallery/tgy_container.py` (writer and reader), `tgy_make.py` (the converter built on it), `tgy_encode.py` (the pixel-source encoder, NOT normative). Vectors: `docs/conformance/tgy_container_v1_vectors.json`; checks: `sim/test_tgy_container.py` (13 tests, 13 mutants), `sim/test_tgy_container_vectors.py`; `make test-tgy-container`. It carries the tile streams of `docs/TGY_SYMBOL_LAYER_V0.md` and defines pixels through `docs/TGY_RECONSTRUCTION_V0.md`. It replaces container version 0 (`tools/gallery/tgy.py`, whole-canvas RAW pictures) for pictures that are coded; a version 1 file may also hold a RAW canvas level, so one reader serves both uses. A reader refuses a file whose version it does not know. **Change control:** anything that changes the meaning of a byte is a new version.

## 1. One file per picture, sections on 4 KB boundaries
Everything is little-endian. A picture is one file (one data slot read target: no per-tile files, no alternating files). Sections start on 4,096-byte boundaries (the APF reads fastest aligned): the first 4,096 bytes hold the header, the level table and the quantisation tables, so ONE 4 KB read is enough to know everything needed to find any tile; then the thumbnail; then, per level in table order, its tile index and its data. The size in the header is the exact size of the file (padded to 4,096): a file of any other size is refused. **Levels are in the order the viewer wants to read them: the fit level first.**

## 2. Header (64 bytes, struct `<4sHHIIBBBBIIIIHHIII` = 52 bytes, then the CRC and 8 zero bytes)
magic `TGY\0`; u16 version (1); u16 header size (64); u32 width, u32 height (the picture with its EXIF orientation applied); u8 channels (1 or 3); u8 reserved (0); u8 EXIF orientation of the FULL level's stored samples (1 to 8; 1 = upright; the fit level and the thumbnail are always upright); u8 flags (0); u32 level count (1 to MAX_LEVELS = 16); u32 level table offset; u32 thumbnail offset; u32 thumbnail length (13,824); u16 thumbnail width and height (96, 72); u32 tables offset; u32 tables length; u32 file size; **u32 CRC-32 of bytes 0 to 51**; 8 reserved zero bytes.

## 3. Quantisation tables
At the tables offset: u16 count (at most MAX_TABLES = 8), then `count` tables of 64 u16 values in **zigzag order**, each at least 1. Levels refer to tables by index.

## 4. Level table (48 bytes per level, struct `<IIHHHHBBBBBBBBIIIIII`)
u32 w, u32 h (the level's size in samples; for the fit level the size of the resampled picture, for the full level the picture's stored size); u16 x, y, w, h (the rectangle of the 800 x 720 viewer canvas the level is shown in); u8 layout (0 raster, 1 tiles); u8 mode (0 RAW, 1 TGY symbol layer v0; 2 is reserved for TGX); u8 pixel format (for tile levels the layout: 0 grey, 1 4:4:4, 2 4:2:0; 0 for RAW); u8 kind (0 RAW fit canvas, 1 full resolution, 2 fit level); u8 quantisation table index of Y, u8 of Cb and Cr; u8 tile size log2 (7: 128); u8 flags (0); u32 data offset, u32 data length, u32 tile index offset, u32 tile index length, u32 CRC-32 of the tile index, u32 reserved.
- **RAW level** (layout 0, mode 0, kind 0): w x h must be 800 x 720, data length 1,728,000: rows of 800 pixels of R, G, B bytes (container version 0's fit canvas, landed straight into the viewer plane).
- **Tile level** (layout 1, mode 1): the picture of w x h samples in the pixel format, cut into 128 x 128 luma tiles in raster order; `rows = ceil(blocks_h / 16)`, `cols = ceil(blocks_w / 16)` where `blocks_w`, `blocks_h` are the Y block counts padded to whole MCUs (grey and 4:4:4: 8 x 8 samples, 4:2:0: 16 x 16); a tile at the right or bottom edge holds only the blocks that exist. **A reader skips a level whose layout, mode or tile size it does not know (flagged unsupported) and refuses a level whose fields are inconsistent.**

## 5. Tile index and tile streams
The tile index has 12 bytes per tile (`rows x cols` entries, raster order): u32 offset of the tile's stream from the level's data offset, u32 length, u32 CRC-32 of the stream. Each stream is exactly what `tgy_v0.encode_tile` produces for that tile's blocks. Streams are concatenated in raster order, not individually aligned. **A tile is decoded alone** (no other tile is needed, any order, any subset): that is what random access, caching and discarding rely on.

## 6. What a reader must check (before it trusts any value)
Magic, version, header size, the header CRC, file size equal to the length of the file, the level table inside the file and 1 to 16 levels, the tables section inside the file, a thumbnail of the exact size inside the file, every table value at least 1, every level's data inside the file, a tile level's tile index of exactly the size its geometry implies and inside the file, the tile index CRC (this also catches two entries swapped, which each tile CRC alone would not), the quantisation table indices below the table count, and per tile: the tile inside the tile range, its offset and length inside the level's data, its CRC. Every damage in this list is refused with an error; a decoder additionally runs under the watchdog (`docs/M3_STREAMING_NOTE.md` section 11, D7). (The level-count bound and the tile-index-size check overlap with the table bounds and the index CRC and are not separately testable.)

## 7. The converter (non-normative behaviour of `tgy_make.py`)
A JPEG (baseline or progressive Huffman; 4:4:4, 4:2:0 or grey) keeps its coefficients **losslessly** as the full level; any other picture is encoded by `tgy_encode` (JPEG standard tables scaled by quality, 4:2:0 for colour, edge replication into partial blocks, no rate-distortion optimisation yet). Both get an encoded fit level (Lanczos resample to fit 800 x 720, never enlarged, centred) written FIRST, and a 96 x 72 RGB565 thumbnail; a picture no larger than the fit size has only the full level. EXIF orientation: recorded in the header; the fit level and the thumbnail are upright; the full level is stored as it is (a viewer that shows it at 1:1 applies the orientation). Measured on the 2560 x 1705 test photo: the full level is 2,398,290 bytes (0.940 of the 2,551,548-byte JPEG), the fit level 158,187 bytes, the whole file 2,588,672 bytes (1.5% above the JPEG: the fit level costs 6%, the saving of the model 6%).

## 8. Conformance
`tgy_container_v1_vectors.json` carries two complete files (a two-level 4:2:0 file and a one-level grey file) with the recorded header, tables, level table, thumbnail hash and the SHA-256 of each level's RGB under the TGY profile. A reader conforms if it parses them to exactly those values; a writer conforms if, given the decoded coefficients, it writes exactly the stored bytes.

## 9. Not defined here
Intermediate zoom levels (DCT-scaled or re-encoded), the metadata section (histogram, EXIF text), TGX levels (mode 2), the index file that lists a folder of pictures for the firmware (`tau-library.tdb` carries the version 0 entries today), and the DC-first progressive preview: the frozen symbol layer codes a tile as one stream, so a coarse picture comes from the fit level, not from a partial read of the full level.
