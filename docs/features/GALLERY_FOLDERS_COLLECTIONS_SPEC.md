# Gallery: folders, collections and the grid's look (a DRAFT spec, to explore later)

Status: **draft for exploration, nothing built** (2026-11-13, from the owner's requests of that day). Not in `docs/ROADMAP.md` order yet: the order is the owner's. Evidence labels in this file: everything below about the Pocket's host is from the APF docs and the skill's notes, not from a test of ours.

## 1. Goal
Show a selection of **folders** first, then the pictures inside the one that is opened (B goes back). Later also **collections**: named groups of pictures that cross folders. And a softer grid: **rounded corners** on the thumbnails and each picture **fitted to a square** instead of showing its own proportions.

## 2. The constraint that shapes everything
The Pocket's host gives a core **no directory listing**: a core reads data slots by file name. Today's library is therefore a **single index file** (`tau-library.tdb`, TGIX: 32 byte header, 160 byte entries with path, name, size, width, height and a thumbnail number, then an atlas of 96 x 72 RGB565 thumbnails, 13,824 B each) that the PC tool (`tools/gallery/`, `merge_index.py`) writes. Folders and collections must be **in the index (or a file beside it) that the PC tool writes**; the firmware cannot discover them on the card.

## 3. Folders
- **Source:** the PC tool walks `Assets/.../photos/<folder>/...` (one level to start; nested folders later) and writes the folder structure into the index.
- **Index change (TGIX version 2, backwards compatible reading of version 1):** entries sorted by folder, then name; a **folder table** after the header: per folder name (up to 26 characters, like picture names), first entry, entry count, cover thumbnail number (default: the first picture's). A version 1 index reads as one folder, "ALL PICTURES", so existing cards keep working.
- **Why contiguous ranges:** a folder is then the range [first, first + n) of entries and the grid code (paging, selection, `gx_entry_off`) works on an offset and a count instead of 0 and `head.count`: a small change, no new indirection in the common path.
- **UI:** level 0 is a grid of **folder tiles** (cover thumbnail, name, picture count, same 4 x 4 paging); A opens a folder (the existing grid with a breadcrumb line "FOLDER NAME  3/12"), B returns to the folder grid and remembers the selected folder; B again behaves as today. The viewer's Left/Right steps within the folder (wraps as today). With a single folder the folder level is skipped.
- **Pseudo-folders:** "ALL PICTURES" (the whole index in folder order) and, later, "COLLECTIONS".
- **Resume** (`gs_resume_index`): remembers folder and index; falls back to the first folder if the folder table changed (index path CRC as now).
- **Size limits to decide:** folders per card (the table is read once into RAM: 40 B each; 256 folders = 10 KB, RAM is 128 KB with about 49 KB bss now), pictures per folder (the entry count is 16 bits today).
- **Tool:** `merge_index.py` learns folders (the merge keeps the card's folders and adds new ones; same rename rule for colliding names), `tau_compat` and its schema learn TGIX version 2 (the DEV 014 stop on an unknown index kind showed what happens otherwise), the installer's dry run lists the folders it would add.

## 4. Collections (explore after folders)
- A collection is a **list of picture references** (index numbers, with the path CRC to detect a changed index), so one picture can be in several. Stored in a second small file (`tau-collections.tdb`, a new data slot) or as a section of the version 2 index; one picture reference is 4 bytes, so 1,000 pictures in collections is 4 KB.
- **Made by the PC tool first** (from a text or JSON list, or a "collections" folder of shortcut files). **On-device editing** ("add this picture to ...", needed for a real feel) needs a **writable data slot**: the Pocket writes saves to a slot declared writable (our settings file does this), so a collections file can be rewritten from the core. Open question to test on a Pocket: how large a rewrite and how often, and what happens when the card is pulled mid-write (keep two copies and a CRC, as the settings do).
- **UI:** the "COLLECTIONS" pseudo-folder lists them like folders; inside, the grid shows references through an indirection (entry = refs[k]); the viewer steps within the collection; Select on the grid could offer "add to collection" later.
- **Open questions:** favourites as a built-in collection; ordering inside a collection (by add time or by name); whether a collection tile's cover is the first picture or a chosen one.

## 5. The grid's look
### 5.1 Square fit
- Today a thumbnail is the whole picture letterboxed in 96 x 72 (the thumbnail the converter writes keeps the proportions). A square that **fills** its cell needs the converter to write a **cover** thumbnail: scale to cover, crop to the square (centre crop; a "smart" crop that keeps faces or the saliency centre is a later option). Cropping at draw time from today's atlas is not enough: a portrait picture's thumbnail has black side bars, so only a sliver of picture is left in a centred crop.
- **Cell size is a design choice** (the screen is 400 x 360 usable, 4 x 4 cells of 96 x 76 today): (a) 72 x 72 squares in 5 columns x 4 rows (20 a page, more pictures, smaller); (b) 96 x 96 squares in 4 columns x 3 rows (12 a page, bigger, shows more detail); (c) keep 4 x 4 with 72 x 72 squares and more air between them. To try on the real screen; the grid math (`cell_xy`, `COLS`, `ROWS`, `PER_PAGE`, paging, the selection frame) is in a few constants and one function, with tests that follow them.
- **The thumbnail atlas changes size** (72 x 72 = 10,368 B, 96 x 96 = 18,432 B instead of 13,824 B): a new TGIX version (the thumbnail size in the header, not a constant), the converter writes it, old indexes still read (their 96 x 72 thumbnails are shown fitted into the cell until regenerated). The detail page's histograms use the thumbnail, so they follow the crop (they would then describe the cropped square): to decide whether the histograms should use a separate small non-cropped sample.
### 5.2 Rounded corners
- Drawn by **masking at draw time**: `draw_thumb` writes two pixels a word through the mailbox; for the first and last few rows the pixels outside a quarter circle of radius r (8 to 12 pixels) are written as the background colour instead (a per-row inset table of r entries, no new data in the file). The selection frame becomes a rounded rectangle of the same radius (a frame drawn by rectangles per row inset, or a one-pixel arc table). Cost: only the corner rows differ, no measurable draw time.
- **Anti-aliasing:** a hard mask is jagged at r = 10; blend the edge pixel with the background colour using a coverage table (2 bits a pixel; the Pocket's screen is small enough that a 1-pixel soft edge matters). The theme's background can vary (theme roles), so the blend uses the theme background at draw time, not a stored colour.
- Folder tiles and collection tiles use the same mask.
- **The Talos engine already has a hardware rounded rectangle (found 2026-11-13, after this section was first written; not yet checked against the gallery's fitted bitstream):** `OP_RRECT` in `src/fpga/core/tau_talos.sv` (B11) fills a w x h rectangle in one colour, then paints the four corner cuts in a background colour; the radius is up to 15 pixels and the cut per row comes from a 16 x 5 bit table the CPU loads (`R_RC_IDX` / `R_RC_DATA`). It is a **solid fill, so it cannot clip a photo**: it would repaint the picture. What it is good for: the **selection frame** (a slightly larger accent-coloured rounded rectangle drawn first, the thumbnail on top), **folder and collection tile backgrounds**, labels and buttons. The photo's own corners still need either the firmware mask above (small, no fit) or a new Talos mode that paints only the corner cuts over what is already there (an RTL change: a unit test, a probe and a full fit of about 1h45, and the owner's yes). Neither `fw2/gfx` nor the gallery firmware has a wrapper for `OP_RRECT` yet. Whether the gallery's build enables it must be read from its configuration before relying on it.

## 6. Tests we would write first (the project's rules)
- **Host, reference + mutants:** the TGIX version 2 reader (folder table, ranges, bad offsets, counts past the file; fuzz with CRC repair like the other parsers), the paging and selection math for a folder range, the corner mask (every pixel of the corner against a circle equation), the cover-crop in the converter (a known picture against a numpy reference), the merge tool (merge keeps folders, renames collisions).
- **App harness:** folder grid, open, back, resume, a single-folder index (level skipped), a folder with 0 pictures (refused by the tool, handled by the reader), a card read failure on the folder table.
- **Pocket:** the look (corner radius, crop, cell size) can only be judged on the real screen; ship a build with a switch on the Info or Settings page to compare cell sizes and radii before fixing them.

## 7. Suggested order (the owner decides)
1. Square fit and rounded corners (small, visible, no new file concept; needs the converter's cover thumbnails and a TGIX thumbnail size field).
2. Folders (TGIX version 2 folder table, tool, UI).
3. Collections (read-only from the PC tool, then on-device editing after a writable-slot test).
